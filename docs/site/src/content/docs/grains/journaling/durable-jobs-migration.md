# 迁移持久化作业存储

持久化作业使用日志存储保存分片元数据和作业记录。
为新分片选择一个写入提供程序，并继续选用之前的提供程序，
以处理完其中的现有作业。大多数部署仅使用一个提供程序；
只有在其他存储命名空间中仍有作业时才需要额外的提供程序。

此过程将**新作业**导向 B，而现有日志继续在原位置排空。
在每个分片的整个生命周期内，仅保留一个权威存储位置。

<a id="prepare-the-bindings"></a>

## 准备绑定

1. 使用命名的
   [Azure Blob/Table](azure-storage.md#named-storage-namespaces)、
   [Redis](redis-journal-storage.md#configure-redis-journal-storage) 或 S3
   日志注册方法注册 A 的现有命名空间和 B 的新命名空间。根据需要使用独立的帐户、容器、表、存储桶
   或键前缀。每个选定的命名空间仅对应一个绑定。
1. 保留 A 的标识、命名空间映射、日志格式读取器和有效载荷
   编解码器。在整个排空期间，其凭据必须允许读取、列举、条件式元数据
   更新、日志写入、压实和删除。
1. 注册 <xref:Orleans.Hosting.DurableJobsExtensions.UseJournaledDurableJobs*>，
   并配置 <xref:Orleans.Hosting.DurableJobsOptions.ActiveProviderName>
   和 <xref:Orleans.Hosting.DurableJobsOptions.DrainingProviderNames>。
   默认写入提供程序名称为 `Default`；排空列表最初为空。
1. 在隔离环境中验证两个命名空间及其权限。启动时会
   验证选定的存储、目录及工厂绑定。实际的存储可用性
   和访问能力仍需要运维检查。

命名日志提供程序通过同一绑定解析存储、目录和状态管理器工厂。
Grain 拥有的
<xref:Orleans.Durable.Journaling.IDurableStateManager> 实例使用的默认提供程序仍独立于显式命名的
持久化作业提供程序。内存和 Azure 持久化作业便捷方法
为默认绑定组合使用同一套通用注册路径。

如需可执行的配置与验证示例，请使用
[持久化作业迁移示例](https://github.com/dotnet/orleans/tree/main/samples/DurableJobsMigration)。
该示例使用磁盘支持的 Azurite，分别运行准备和排空控制台进程，
持久化未来作业的句柄，重启后恢复并执行 A 中的作业，在 B 中创建
作业，并在本地报告完整清单。命名提供程序 API 要求
使用包含此功能的源码构建软件包；仓库的示例
构建流程会提供这些软件包。

<a id="stage-the-deployment"></a>

## 分阶段部署

提供程序的选择在进程启动时确定。变更绑定或选择时，
请重启 Silo。

| 阶段 | 写入提供程序 | 排空提供程序 | 必须满足的条件 |
| --- | --- | --- | --- |
| 稳定状态 | A | 空 | 所有作业均位于 A |
| 准备 | A | B | 在 B 接收新作业之前，每个负责调度的 Silo 都可以发现并定位 A 和 B |
| 切换 | B | A | 使用此选择重启所有负责调度的 Silo，并完成先前的调度调用 |
| 退役 | B | 空 | 首先验证已完全排空，并停止所有剩余的 A 写入方 |

在普通滚动切换期间，仍配置为 A 的旧 Silo 依然可以创建
A 分片。应将部署完成和已获准执行的调度调用全部结束
视为切换边界的一部分。如果应用需要严格的切换时间，
请暂停应用的调度操作，完成正在进行的调度，更新所有负责调度的
Silo，验证配置，然后恢复调度。

保留 A 的凭据和命名空间，直至最终清理完成。在 B 接收新作业期间，
A 中的现有作业仍继续变更 A 中的数据。

正常关闭期间，每个 Silo 会处理完已接受的请求并停止活动作业的执行尝试，
然后释放非空分片以供其他 Silo 认领，同时
删除空分片日志。这也包括正在等待未来
开始时间或队列变化的活动分片。清理受宿主关闭截止时间约束，因此应为
存储操作预留时间，并在退役提供程序之前调查日志记录的所有权或清理
失败。

<a id="understand-routing-during-the-drain"></a>

## 了解排空期间的路由

新调度使用在 B 中新建的分片。发现过程扫描 A 和 B，采用统一的
最早优先顺序和总认领预算，然后使用分片所在提供程序的
绑定打开各个分片。执行、所有权变更、
重试、重新调度、取消、快照和删除均保留该绑定。
排空中的分片始终不接受新调度。

分片 ID 保留时间戳/GUID 表示形式，日志 ID 仍为
`jobs/shards/<id>`。序列化的 <xref:Orleans.Durable.Jobs.DurableJob> 句柄保留
其现有的、与提供程序无关的结构。
切换后，应用代码可继续使用此前保存的句柄。

对于已知但未缓存的分片：

- 仅选用一个提供程序时，运行时读取该提供程序的元数据，
  且直接读取，无论还注册了哪些其他
  提供程序，此路径都仅执行一次元数据读取。
- 选用多个提供程序时，首先按确切的日志 ID 查询写入提供程序，
  然后按需查询排空提供程序。此查找也可以找到
  正常发现前瞻范围以外的未来分片。
- 定位分片后，各项操作均使用其原始绑定。已跟踪的
  分片已具有此绑定。

只有在所有选定提供程序中成功检查并确认不存在，才能确定分片不存在。
若提供程序故障导致查找无法确定结果，则会抛出
<xref:System.AggregateException>。如果另一提供程序提供了权威分片，
则可使用其绑定，同时先前的故障仍可被观测到。
发现过程按各提供程序的配置名称报告其故障。后续新一轮
扫描会重试失败的提供程序。

每轮扫描按配置顺序枚举选定的目录，并缓冲各
提供程序的候选分片，直到其枚举成功。只有所有选定目录均完成或发生故障后，
才开始分配分片，并对成功获取的结果采用共享的
最早优先认领预算。目录故障会丢弃该
提供程序的部分结果。

因此，恢复延迟包括目录列举请求和存储客户端的
重试延迟。请为每个存储客户端配置请求超时及重试上限，
以满足所需的恢复延迟，并在排空期间监控目录延迟。
分片检查间隔负责安排新的扫描；存储客户端设置
则控制待处理请求的尝试。

<a id="verify-retirement"></a>

## 验证退役条件

从宿主的服务中解析 <xref:Orleans.Durable.Jobs.IDurableJobsStorageInspector>，
并调用其 <xref:Orleans.Durable.Jobs.IDurableJobsStorageInspector.InspectAsync*>
方法，传入 A 的配置名称和取消令牌。
返回的 <xref:Orleans.Durable.Jobs.DurableJobsStorageStatus> 描述完整的
`jobs/shards/` 目录快照，由调用方通过只读目录及
元数据操作获取。它包括前瞻范围之外的未来分片以及需要运维人员恢复的
有毒分片。

| 结果 | 运维含义 |
| --- | --- |
| `ProviderName`、`IsWriteProvider` | 调用方配置的绑定及写入选择 |
| `ShardCount` | 分片命名空间中现有日志的数量，包括未识别的条目；每个已识别分片可包含多个作业 |
| `OwnedShardCount` | 元数据中记录了所有者的分片数量；应通过集群成员资格单独判断所有者是否存活 |
| `PoisonedShardCount` | 需要调查才能继续正常处理的分片数量 |
| `UnrecognizedShardCount` | 分片元数据无法解释的条目数量；退役之前应处理这些条目 |
| `OldestShardStartTime`、`NewestShardStartTime` | 来自已识别分片时间窗口元数据的可空边界；重试及重新调度可能使执行尝试超出这些窗口 |

计数为 64 位值。已拥有分片与有毒分片的计数可能重叠。检查
失败或取消会使操作以失败结束。成功结果覆盖
完整的枚举。失败时显示**未知**并保留错误信息。

移除 A 之前必须满足以下全部条件：

- 所有负责调度的 Silo 和其他 A 写入方均已完成切换，且先前的调度
  请求已结束。
- 成功的完整清单报告分片总数为零，
  包括未识别条目。
- 未来到期、已有所有者、有毒及反复重新调度的作业均已
  通过应用的恢复或取消流程处理。
- 作业完成和空分片删除均已成功；存储授权及
  清理错误均已调查。
- 根据后端实时列举语义要求执行的重复清单检查，
  与部署证据一致。
- 同一绑定的其他使用方已停止使用该绑定。

退役既要求成功获得完整且总数为零的清单，也要求
集群范围内所有写入方完成切换。清单是一次实时观察结果，且
`IsWriteProvider` 反映执行检查的进程的配置。应保存
每个写入方完成切换的独立部署证据，以及
每次成功检查清单的时间。

满足这些条件后，从排空列表移除 A，并仅使用 B 重启。
仅在其他使用方也已结束使用后，才退役 A 的存储绑定和凭据。
运行时将恢复单提供程序直接查找路径。
对于已完成作业的句柄，当其分片不存在时，
仍保持现有的取消结果语义。

<a id="roll-back-safely"></a>

## 安全回滚

保持两个提供程序均被选用，并保留支持提供程序感知的二进制文件。将写入
切回 A，同时排空 B，遵循相同的分阶段部署流程。现有
B 分片继续执行并变更 B 中的数据。回滚窗口期间应保持两个命名空间、权限、
格式读取器及有效载荷编解码器可用。

<a id="monitor-and-diagnose"></a>

## 监控与诊断

遵循[按提供程序监控排空进度](operations.md#monitor-durable-jobs-provider-draining)的指导。
在记录部署版本及已配置的提供程序名称时，一并记录清单检查的时间戳
和失败信息。成功检查会发出结构化的
Information 级别清单日志；提供程序故障会发出包含配置名称的结构化 Error 级别
日志。结合现有持久化作业及日志指标，使用这些日志和检查器快照
跟踪各提供程序的进度。

| 现象 | 检查与处理 |
| --- | --- |
| 启用 B 后 A 的计数仍增长 | 查找仍配置为创建 A 分片的 Silo 或其他写入方；评估退役之前先完成切换 |
| 到期作业执行空闲时 A 仍非空 | 检查整个命名空间中是否存在未来到期、有毒、已有所有者或反复重新调度的作业 |
| A 中的作业在执行，但计数仍大于零 | 调查剩余可写分片、重试或重新调度活动以及空分片删除失败 |
| 切换后的取消操作报告存储错误 | 检查每个选定提供程序的可达性和变更权限；保留存储错误，在重试请求之前恢复访问 |
| 某个提供程序的清单已过时 | 将其状态标为未知；检查列举、元数据读取、限流和授权 |

大型目录的清单检查可能开销很高。应以受控频率运行检查，
为运维操作设置有限超时时间，限制运维结果的访问，
并避免将凭据写入日志。示例通过本地
控制台输出报告清单。部署新增的任何运维接口都应
应用身份验证和授权。
