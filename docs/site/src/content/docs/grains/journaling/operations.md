# 运维与排查 Orleans Journaling

Orleans Journaling 是实验性的 Alpha 功能。在生产环境中进行评估时，应为软件包升级、存储格式迁移、回滚、备份、还原、压实和提供程序中断指定负责人，并制定经过测试的流程。

<a id="monitor-writes-and-recovery"></a>

## 监控写入与恢复

Journaling 通过 `Microsoft.Orleans` Meter 发出指标。完整的指标检测器列表参见[指标目录](../../host/monitoring/metrics-catalog.md#journaling)。

至少为以下指标建立仪表板及告警：

- 按 `append`、`snapshot`、`replace`、`read` 和 `delete` 分类的存储操作错误及延迟。
- 恢复失败次数及恢复耗时。
- 存储操作排队时长，反映等待同一日志中较早操作完成的时间。
- 按 `storage_requested`、`migration` 和 `user_snapshot` 分类的压实触发次数。
- 写入合并情况、已汇集的状态数量及操作字节数分布。
- 按 `provider` 分组的目录页数及候选项数量。
- 原生列举项数与实际交付的目录条目数的对比，以及提供程序显式重试率。

将这些信号与 Grain 标识、提供程序依赖项健康状态、部署版本及存储限流情况关联分析。

<a id="monitor-durable-jobs-provider-draining"></a>

### 监控持久化作业提供程序排空

在 Journaling 目录指标中，分别跟踪已配置的提供程序名称及后端类别。两个命名 Blob 提供程序使用相同类别的后端，但可用性和剩余工作量可能不同。

使用 <xref:Orleans.Durable.Jobs.IDurableJobsStorageInspector.InspectAsync*> 为每个选定提供程序收集完整的分片命名空间快照。记录清点的开始和完成时间戳、调用方、已配置的写入提供程序、成功或失败状态、计数及最早和最晚的分片开始时间。保留上次成功结果及其时间戳作为历史记录；失败时将当前状态标记为未知。

检查成功时，还会发出结构化的 Information 级别清点日志。提供程序错误会发出包含已配置提供程序名称的结构化 Error 级别日志。使用检查器快照和这些日志跟踪各提供程序的排空进度；现有执行及目录指标则提供补充的工作负载信号。

切换期间，应针对旧提供程序写入权限失败、发现失败或已知 ID 查找失败、清点失败、毒化或无法识别的条目，以及异常停滞的排空曲线发出告警。每个分片可能包含许多作业，重试或重新调度可能将其生命周期延长到原始时间窗口之外。最早和最晚的分片开始时间描述已识别分片的时间窗口；重试及重新调度可能使执行尝试超出这些窗口。

常规发现使用前瞻范围限制，并可能跳过未来的工作或毒化工作。使用完整的检查器结果及[退役检查清单](durable-jobs-migration.md#verify-retirement)中的部署证据，判断旧存储是否可以移除。执行吞吐量及对符合条件工作的扫描提供补充的工作负载信号。将检查作为受保护的运维命令或后台诊断任务运行，并对运维接口实施身份验证及授权。

<a id="monitor-catalog-traversal-and-retries"></a>

### 监控目录遍历及重试

使用 `orleans-journaling-provider-catalog-pages` 跟踪 S3 和 Azure 目录遍历期间收到的页数，包括空页。比较 `orleans-journaling-provider-catalog-items` 和 `orleans-journaling-provider-catalog-entries`，了解有多少返回的候选项在到达使用方前被筛除。Redis 的候选项计数包括筛选和去重之前已消费的扫描键。易失性存储记录已交付的条目。

`orleans-journaling-provider-retries` 记录提供程序存储恢复循环中的显式重试。将重试率与现有 Journaling 指标及提供程序专用的存储延迟和结果指标关联分析。目录页、候选项及条目数反映遍历工作量；进行成本核对时，应使用服务端事务指标。

<a id="use-host-provided-dependency-telemetry"></a>

### 使用宿主提供的依赖项遥测

应用程序通过托管集成、检测库及诊断配置提供客户端 SDK 遥测。例如，Aspire 集成可以为其注册的客户端启用依赖项遥测。调查 SDK 请求延迟、故障及传输重试时，应复用现有检测功能。额外的诊断数据收集应在应用程序的客户端配置中进行：

| 提供程序 | 可选启用的诊断 |
| --- | --- |
| Azure Blob 和 Table | 按照 [Azure SDK 日志记录](https://learn.microsoft.com/dotnet/azure/sdk/logging) 的说明附加事件侦听器，或将 SDK 事件转发到应用程序日志。请求及响应事件包括 HTTP 状态和 I/O 耗时。 |
| S3 | 在应用程序启动时、构造 S3 客户端之前配置 [AWS SDK 日志记录](https://docs.aws.amazon.com/sdkfornet/v4/apidocs/items/Util/TLoggingConfig.html)。选择日志目标并启用 SDK 指标日志记录，以诊断请求。 |
| Redis | 使用 [StackExchange.Redis 性能分析](https://seredis.dev/Profiling_v2) 在提供程序的连接多路复用器上注册性能分析器。将会话限制在调查的工作范围内，并结束每个会话以收集命令排队、发送及响应耗时。 |

应用程序控制诊断数据收集、导出器及保留策略。将详细收集限制在必要的时间区间内，并使用 SDK 的日志控制机制及应用程序的数据处理策略保护资源标识和响应内容。共享客户端保留现有诊断配置，生命周期仍由调用方管理。

<a id="plan-capacity"></a>

## 规划容量

日志重放成本随最近一次快照以来的字节数和操作数量增长。快照成本随 Grain 的完整持久化状态增长。

容量测试应包括：

- 预期最大的持久化集合及持久化状态有效载荷。
- 频繁写入的热点 Grain 标识。
- 长序列追加后的激活。
- 流量高峰期间提供程序请求的压实。
- 存储限流、暂时性故障及乐观并发恢复。
- 备份及还原之后的激活和再次写入。

在重放时间、存储增长或后端事务限制成为运维风险前调整提供程序阈值。[Azure Table 提供程序](azure-storage.md#azure-table-storage)将单个追加批次限制为 2 MiB。Redis 默认在 128 MiB 时请求压实。Azure Blob 在耗尽追加块数预算之前执行压实。

<a id="upgrade-and-rollback"></a>

## 升级与回滚

将软件包版本、公共 API、日志格式、应用程序有效载荷架构和持久化状态名称视为同一兼容性契约。

1. 备份日志字节及元数据。
1. 在隔离环境中使用候选二进制文件验证旧数据。
1. 让所有能够激活日志化 Grain 的 Silo 使用经过测试的兼容版本组合。
1. 在写入方仅输出新架构之前，先部署支持新旧有效载荷架构的读取器。
1. 观察恢复及迁移压实指标。
1. 在整个回滚窗口内保留旧的读取器、编解码器及状态定义。

提供程序键前缀、Blob 名称映射、Table 分区映射、日志格式键或持久化状态名称决定运行时如何查找及解释现有数据。在新的映射开始处理流量前，执行并验证相应的数据迁移。

<a id="backup-and-disaster-recovery"></a>

## 备份与灾难恢复

提供程序元数据选择已发布的世代编号及日志格式。以一致的方式备份元数据和日志数据。将两者作为整体还原，并保持相同的应用程序 `ServiceId`、Grain 标识、状态名称、格式读取器及有效载荷编解码器。

定期演练还原流程：

1. 还原到隔离的提供程序命名空间。
1. 启动兼容的 Silo。
1. 激活有代表性的 Grain 并验证恢复出的状态。
1. 执行一次新写入并等待确认。
1. 触发或等待压实，然后验证第二次激活。

<a id="diagnose-common-failures"></a>

## 诊断常见故障

| 症状 | 运行时结果 | 运维人员的处理措施 |
| --- | --- | --- |
| 激活因日志格式键而失败 | 恢复不会改变存储 | 部署所需格式及命令编解码器，或还原指定实际已存储格式的元数据 |
| 激活报告日志数据格式错误或被截断 | 恢复在激活完成前停止 | 隔离写入操作、还原一致性备份，并保留故障数据供诊断 |
| 写入期间发生 <xref:Orleans.Storage.InconsistentStateException> | 管理器阻止后续操作并请求停用；新的激活实例恢复持久化状态 | 查找过时或竞争的写入方，确认 Grain 标识和集群配置，再依据幂等性契约重试应用程序命令 |
| 存储提交了写入，但确认丢失 | 管理器阻止后续操作并请求停用；新的激活实例观察到已提交的变更 | 使用操作标识符对账，且仅通过幂等性协议重试命令 |
| <xref:Orleans.Durable.Journaling.JournaledStatePreCommitException> 报告状态准备失败 | 存储操作未执行，待处理变更仍然可用 | 恢复先决条件并显式重试日志写入，保留已暂存的业务结果 |
| 写入延迟随存储排队时长增加 | 该日志的写入正在等待先前操作 | 检查提供程序延迟及限流、热点 Grain 流量、写入频率和快照大小 |
| 恢复时间及日志字节数增长 | 当前追加历史记录较大 | 确认压实阈值已启用，且快照替换成功 |
| 格式迁移报告未注册的状态 | 已退役的状态流仍需要先前的编解码器 | 为迁移重新注册该状态，或保留先前的写入格式，直到退役及压实将其移除 |
| 服务器故障后 Redis 状态丢失 | 恢复结果取决于 Redis 持久性配置 | 根据所需恢复点配置并测试 Redis 持久化及复制 |

存储及编解码器异常会传递到 Grain 调用。应在日志和跟踪中保留这些异常，而不是将其转换为应用程序成功响应。
