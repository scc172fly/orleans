# 排查 Orleans 运行故障

请将这些运维手册作为排查步骤，而不是某个根本原因的直接证据。在更改配置之前，记录故障时间范围、部署变更、集群拓扑和流量水平。当用户受到的影响不断扩大时，优先考虑回滚或减少流量。

如果从异常、日志事件、指标或错误原文开始排查，请使用 [Orleans 故障现象和信号目录](troubleshooting-symptom-catalog.md)。

<a id="client-cant-connect"></a>

## 客户端无法连接

**证据：** 没有已连接的网关、反复连接失败、<xref:Orleans.Runtime.Messaging.ConnectionFailedException>，或者仪表板或客户端报告已失去集群连接。

1. 确认客户端与 Silo 使用相同的集群 ID、服务 ID 和集群提供程序。
2. 从客户端所在的网络边界查询成员资格或网关信息源，确认其返回处于活动状态且公布的网关地址可达的 Silo。
3. 测试这些地址的 DNS 解析和 TCP 连通性。检查防火墙、网络策略、NAT 和负载均衡器。
4. 如果启用了 TLS，请检查握手错误、证书有效性、SAN/`TargetHost`、信任链、EKU，以及 Silo 是否意外要求客户端证书。
5. 比较所有 Silo 的日志。一个可达网关可能掩盖部分路由故障。

不要在启动阶段无限重试。限制启动和重新连接行为；当客户端没有可用网关时，将就绪状态报告为 false。

<a id="grain-calls-time-out"></a>

## Grain 调用超时

**证据：** `orleans-app-requests-timedout` 增长、请求延迟较高，或调用方出现 <xref:System.TimeoutException>。

1. 从调用方追踪一条采样链路，确定调用是否到达 Silo，以及等待发生在 Grain 执行之前、Grain 内部还是某个依赖项中。
2. 将超时增长与拒绝或丢弃的消息、网关连接、长时间运行的执行轮次、CPU、线程池饥饿、GC 暂停和存储延迟进行对照。
3. 检查超时是否随部署、流量增长、成员资格变更或依赖项降级而开始出现。
4. 检查目标 Grain 类型和操作。查找阻塞调用、锁争用、同步 I/O、扇出调用或不遵循取消请求的调用。
5. 仅当操作的合理延迟超过现有时间预算时，才增大超时时间。增大超时时间不能解决过载或执行轮次阻塞，还可能增加排队的工作量。

<a id="membership-is-unstable"></a>

## 集群成员资格不稳定

**证据：** Silo 反复退出 `Active` 状态、探测响应缺失，或整个集群出现成员资格警告。

1. 比较各 Silo 的成员资格视图和时间戳。在将变更判定为故障之前，先考虑是否正在进行有计划的滚动部署。
2. 检查宿主暂停、CPU 饥饿、GC 暂停、丢包、DNS 变更及时间同步。
3. 从每个 Silo 验证成员资格存储的延迟、可用性、凭据和限流情况。
4. 确认公布的 Silo 地址稳定且相互可达；不要跨宿主公布环回地址或临时地址。
5. 在了解基础设施停顿和存储延迟之前，不要放宽存活检测设置。延长检测时间可能减少误报，但也会延迟故障恢复。

<a id="grain-turns-appear-stuck"></a>

## Grain 执行轮次似乎卡住

**证据：** `orleans-scheduler-long-running-turns` 增长、某个 Grain 的队列变长，或链路跟踪显示应用程序执行耗时很长。

1. 利用链路跟踪、仪表板性能分析和日志确定 Grain 类型及方法。
2. 在问题发生时捕获进程跟踪或转储。检查托管调用栈、CPU 消耗者、线程池队列和监视器锁争用。
3. 查找同步阻塞（`.Result`、`.Wait()`）、无界循环、CPU 密集型工作、无超时限制的外部调用，以及因循环调用而互相等待的不可重入 Grain。
4. 在重启之前减少传入负载或隔离受影响的操作。重启会清除证据，可能只是将阻塞转移到其他地方。
5. 将阻塞或 CPU 密集型工作移出 Grain 执行轮次，或者将其拆分为有界的异步步骤。

<a id="storage-operations-fail"></a>

## 存储操作失败

**证据：** Orleans 存储错误指标增长、存储跟踪跨度失败、激活失败或出现提供程序异常。

1. 区分读取、写入和清除操作，并确定存储提供程序与 Grain 类型。
2. 从受影响的 Silo 检查后端健康状况、限流、身份验证、DNS/TLS、连接池和延迟。
3. 确定失败属于暂时性故障、并发或 ETag 冲突、序列化失败，还是确定性的数据或架构问题。
4. 比较受影响的 Silo 和分区。仅一个宿主受影响可能意味着本地连接或凭据问题；同一分区受影响可能意味着后端存在热点。
5. 不要无限重试确定性的序列化或并发失败。对于提供程序文档明确说明的暂时性故障，采用有界重试并保持幂等性。

<a id="the-cluster-is-overloaded"></a>

## 集群过载

**证据：** 消息被拒绝、网关执行负载削减、队列或延迟不断增长、CPU 使用率较高，或需求增加时吞吐量反而下降。

1. 确认压力位于网关、Grain 执行、存储、流还是其他依赖项。
2. 比较各 Silo 的请求速率、完成速率、延迟、拒绝次数、激活实例数量、CPU、线程池及 GC。
3. 减少准入量或削减可选工作。立即重试被拒绝的工作会加剧过载；在适当的边界采用带随机抖动的有界指数退避。
4. 仅当工作能够分散到新增 Silo，且瓶颈不是共享依赖项或热点 Grain 时，才进行扩容。
5. 恢复后，将容量告警阈值设在开始拒绝请求之前，并针对触发故障的流量模式添加负载测试。

<a id="memory-pressure-rises"></a>

## 内存压力上升

**证据：** `orleans-runtime-available-memory` 较低、进程工作集或 GC 堆增长、GC 暂停时间较长、容器因 OOM 被终止，或激活实例频繁回收。

1. 比较进程工作集、GC 堆大小、分配速率、回收次数和暂停时间、Orleans 激活实例工作集及流缓存指标。
2. 检查实际的容器或宿主内存限制。物理宿主的可用内存可能无法准确反映容器化进程的内存状况。
3. 如果安全可行，在重启之前捕获转储或 GC 跟踪。按类型和引用保留路径对仍被保留的对象分组。
4. 检查无界的 Grain 状态、缓存、流缓冲区、请求有效载荷、遥测基数和激活实例增长。
5. 减少负载或横向扩展以恢复稳定。不要在尚未确定内存使用是否受到有意限制之前直接提高内存限制。

<a id="shutdown-doesnt-complete"></a>

## 关闭过程未完成

**证据：** 编排器在宽限期结束后强制终止 Silo、成员资格状态一直停留在 `ShuttingDown`/`Stopping`，或日志报告优雅关闭过程已中止。

1. 比较宿主关闭超时时间与编排器终止宽限期。在强制终止之前为 Orleans 和其他托管服务留出停止时间。
2. 在停止 Silo 之前停止接收新的外部工作。
3. 检查最后的生命周期日志和跟踪，查找长时间运行的 Grain 调用、停用过程、成员资格存储更新、流关闭或受阻的托管服务。
4. 确保 <xref:Orleans.ILifecycleObserver.OnStop*> 遵循取消请求，且自定义生命周期参与者能够及时完成。
5. 将反复发生的强制终止视为可用性风险。修复造成阻塞的组件，而不是依赖强制终止进程。

<a id="preserve-diagnostic-evidence"></a>

## 保留诊断证据

对于间歇性或仅在生产环境出现的故障，请保留：

- UTC 时间戳及部署或版本标识符。
- 所有相关客户端和 Silo 的日志。
- 覆盖事件发生前、发生期间及发生后的指标。
- 具有代表性的跟踪 ID 和未经采样的请求计数。
- 成员资格快照及提供程序健康状况。
- 当涉及调度器、CPU 或内存行为时，保留进程跟踪或转储。

共享诊断材料之前，请移除机密和 Grain 状态中的敏感信息。有关 `dotnet-counters`、`dotnet-trace` 和转储收集的指导，请参阅 [.NET 诊断](https://learn.microsoft.com/dotnet/core/diagnostics/)。
