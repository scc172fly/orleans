# 流投递、顺序、重放和恢复

Orleans 流 API 不承诺一种普遍适用的投递保证。所选提供程序及其底层服务决定何时接受事件、投递失败后是否重试、可以观察到怎样的顺序，以及旧事件是否仍然可用。

Orleans 本身不保证恰好一次投递或处理。网络故障可能使发布结果无法确定，持久化提供程序也可能重复投递事件。

<a id="exactly-once-effects"></a>

## 恰好一次的副作用

应用程序可以在事务边界内实现可观察副作用的恰好一次执行。为每个事件指定稳定的标识值，例如应用程序定义的事件 ID；只有提供程序保证令牌在重复投递时保持稳定，才可使用提供程序的 <xref:Orleans.Streams.StreamSequenceToken>。以原子方式同时提交事件的副作用和该标识已处理的记录。重复投递时，跳过已提交的标识。

仅记录序列令牌是不够的。如果消费者先记录令牌再应用副作用，两项操作之间的故障可能导致副作用丢失。如果先应用副作用再记录令牌，故障可能导致副作用被再次应用。副作用与检查点必须在同一次原子提交中完成，或者副作用的目标系统必须提供等效的去重机制。

对于该事务之外的副作用，请使用幂等键、事务性收件箱或发件箱，或者能拒绝重复事件 ID 的目标系统。序列令牌的作用域及稳定性取决于提供程序。不可回溯的队列提供程序的令牌可能表示读取位置，并可能在事件重复投递时发生变化。除非提供程序明确保证其令牌适用于去重，否则应使用应用程序事件 ID。

<a id="producer-acknowledgment"></a>

## 生产者确认

<xref:Orleans.Streams.IAsyncObserver`1.OnNextAsync*> 返回的任务在提供程序根据自身契约接受该项并承担责任时完成。对于持久化提供程序，通常是在底层服务接受事件之后。它并不证明所有订阅者都已处理完成。

生产者超时或收到异常，意味着未能确认事件已被接受。该项可能尚未被接受，也可能只是确认消息丢失。重试可能产生重复项，因此只要存在重试的可能性，就应包含应用程序事件 ID。

<a id="consumer-acknowledgment-and-retries"></a>

## 消费者确认与重试

消费者的 `OnNextAsync` 任务表示该消费者何时已接受该项并承担处理责任。对于队列型提供程序，如果投递在成功完成之前失败，通常会保留该项或重新投递。重试可能延迟后续项，并改变观察到的顺序。

不要在必要的状态变更或副作用得到可靠记录之前确认消费成功。也不要为了无关的后台工作而让任务一直处于未完成状态；这会占用投递容量并增加队列和缓存压力。

<a id="ordering"></a>

## 顺序

将顺序视为具有特定作用域，而非全局顺序：

- 等待每次发布调用完成，可以让同一个生产者按顺序提交，但并发生产者之间没有共享顺序。
- 各物理分区和队列独立排序。
- 重试、可见性超时、消费者故障和再均衡都可能改变投递顺序。
- 除非并发配置另有规定，否则 Grain 串行处理自身的执行轮次；但这并不意味着不同 Grain 或订阅之间存在全序关系。
- 无状态工作者的流订阅将每次投递尝试分配给一个选定的激活实例。并发投递及重试可能在不同激活实例上运行，因此工作者池中的完成顺序没有规定。

当业务逻辑要求顺序时，请使用事件版本号或领域序列号。<xref:Orleans.Streams.StreamSequenceToken> 表示提供程序中的位置，并不是通用的业务序列号，而且并非所有提供程序都接受应用程序提供的令牌。

<a id="replay-and-rewindability"></a>

## 重放与回溯能力

当相应事件仍位于提供程序的保留窗口内时，支持回溯的提供程序可从某个提供程序序列令牌开始或恢复订阅。可回溯性不同于持久性：

- 内存流只能在临时内存缓存的范围内回溯。
- Event Hubs 和 Redis Streams 可以在保留的外部数据范围内回溯。
- Azure Queue、Amazon SQS、ADO.NET 和 NATS JetStream 提供程序不支持回溯。

显式订阅可以根据提供程序的令牌语义从仍然保留的位置恢复。隐式订阅在激活实例附接其观察者时接受恢复令牌，然后在该次附接期间单调向前推进。一旦有一次投递调用成功完成，再使用序列令牌恢复活动的隐式订阅句柄将抛出 <xref:System.InvalidOperationException>；传入 `null` 则会在当前位置替换观察者。

对于支持回溯的持久化流，新建显式订阅时也可以选择[相对于缓存的起始位置](subscription-start-positions.md)。有关各提供程序的能力，请参阅[提供程序对照表](stream-providers.md#provider-matrix)。

<a id="recovery-checklist"></a>

## 恢复检查清单

1. 如果已接受的事件必须在 Silo 或集群丢失后仍能恢复，请使用持久化提供程序。
1. 如果显式订阅记录必须在集群丢失后仍然存在，请使用持久化的 [`PubSubStore`](pubsub-storage.md)。
1. Grain 激活后恢复已有的显式订阅句柄，不要无条件调用 <xref:Orleans.Streams.IAsyncObservable`1.SubscribeAsync*>。
1. 如果应用程序需要确定性恢复，请持久化最后应用的领域位置。
1. 对于支持回溯的提供程序，从检查点记录的令牌重新开始，并容忍检查点边界的重复重放。
1. 使副作用具有幂等性，并针对有毒事件、反复重试和持续增长的积压延迟发出告警。

提供程序的数据保留和订阅存储解决的是不同的问题。只有持久化事件而没有持久化订阅元数据，事件可能因没有消费者绑定而一直等待；只有持久化订阅而使用临时提供程序，则无法恢复已消失的事件。
