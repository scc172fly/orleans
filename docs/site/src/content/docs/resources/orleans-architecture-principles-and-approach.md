<a id="orleans-architecture-design-principles"></a>

# Orleans 架构设计原则

Orleans 旨在帮助 .NET 开发者构建有状态的分布式应用，而无需让每个应用从基本原理出发自行实现标识、放置、生命周期、消息传递及成员资格。

<a id="familiar-programming-model"></a>

## 熟悉的编程模型

Orleans 使用 .NET 接口和类表示分布式实体。调用是异步的，以显式体现网络边界；依赖注入、托管、配置、日志及测试则采用标准 .NET 模式。

熟悉的编程方式不意味着 Grain 调用等同于本地方法调用。序列化、延迟、部分故障、取消及重试仍然属于 API 设计的一部分。

<a id="identity-independent-of-activation"></a>

## 与激活实例无关的标识

即使内存中没有激活实例，Grain 的逻辑标识仍然稳定。Orleans 可以按需激活 Grain、将其放置在 Silo 上、将调用路由至该 Grain，并在空闲时移除激活实例。

这一间接寻址机制是位置透明性和资源管理的基础。这也意味着应用应避免在领域契约中编码进程位置。

<a id="isolation-and-partitioning"></a>

## 隔离与分区

Grain 封装状态，默认每次处理一个执行轮次。这有利于采用由许多可独立寻址实体组成的设计，并减少共享内存协调。

Orleans 提供可扩展的基础构件，并非使每种模型都自动具有可扩展性。Grain 边界、键分布、调用模式、外部依赖及存储选择决定了应用如何扩展。

<a id="recovery-oriented-operation"></a>

## 面向恢复的运行方式

检测并修复问题，不要假定能够完全预防问题。在云规模下，故障经常发生，甚至看似不可能发生的事情也会发生，只是频率较低。预防及容错机制仍然有价值，但无法涵盖硬件、软件、依赖项或运维中的所有故障。因此 Orleans 采用通常称为*面向恢复的计算*的方法来补充这些机制：预期存在无法预防的故障，检测故障并恢复服务。

实际上，Orleans 检测成员资格变化，并能在故障后于健康 Silo 上重新激活 Grain。正在进行的调用仍可能失败，易失状态会随进程丢失。

因此，应用需要显式的持久性保证、幂等性、有界重试、可观测性及运维流程。运行时处理通用机制，但不会替应用定义应用级恢复语义。

<a id="extensible-providers"></a>

## 可扩展的提供程序

集群成员资格、持久化、提醒器、流、持久化作业、序列化及相关服务公开提供程序模型。应用可以选择适合其环境的基础设施，也可以实现自定义提供程序。

提供程序边界使编程模型具有可移植性，但每个后端仍有自身的限制、一致性、可用性、身份验证及运维特征。

<a id="make-the-safe-path-straightforward"></a>

## 让安全做法易于采用

Orleans API 旨在引导应用采用异步执行、隔离状态、稳定的序列化契约及受管理的生命周期。默认行为面向普遍适用的场景，同时在需求充分时允许高级放置、并发及提供程序自定义。

设计优先目标是为常见有状态分布式应用提供一致的基础，而非为每种分布式工作负载提供通用抽象。
