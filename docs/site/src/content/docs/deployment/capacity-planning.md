# 容量规划与扩缩容

Orleans 将激活实例和工作分布到各个 Silo。容量需求取决于活跃的工作负载：Grain 可能处于空闲状态，也可能是 CPU 密集型、内存密集型、热点 Grain，或因等待依赖项而阻塞。

<a id="plan-for-scale"></a>

## 为扩展规模制定计划

Orleans 将 Grain 激活实例和请求处理分布到各个 Silo。应用程序直接寻址 Grain 标识，Orleans 按需创建激活实例；增加 Silo 可以为能够按激活实例分散的工作负载提升容量。

实际可运行的负载范围取决于应用程序和环境。应通过有代表性的测试来确定这一范围，测试涵盖工作负载、主机资源、网络、存储和集群提供程序、外部依赖项及恢复要求。一个 Grain 标识首次被使用时，其激活实例才开始消耗资源，因此应根据活跃工作负载和资源使用情况确定集群容量。

有关支持横向扩容的机制，请参阅[拓扑、网络与集群](networking.md)、[集群成员资格协议](../implementation/cluster-management.md)和 [Grain 目录架构](../implementation/grain-directory.md)。

<a id="establish-a-workload-model"></a>

## 建立工作负载模型

对接近生产环境的混合工作负载测量以下指标：

- 各项操作的每秒调用次数及延迟目标。
- 按 Grain 类型统计活跃数量及总数量。
- Grain 状态大小、读写频率和序列化开销。
- 热点键的集中程度，以及向其他 Grain 或服务扇出的调用。
- 定时器、提醒器、流及后台工作。
- 有效载荷大小和客户端网关流量。
- 依赖项的延迟、限流和连接数限制。

负载测试应包括突发流量、单个 Silo 丢失、滚动替换、依赖项性能下降，以及积压后的恢复场景。

<a id="measure-activation-throughput"></a>

## 测量激活吞吐量

激活和停用的吞吐量因提供程序延迟、状态大小、应用程序生命周期代码、资源争用以及 Silo 的规格而异。冷调用可能涉及目录查找及注册、放置决策、对象构造、持久化状态读取和应用程序激活回调。停用可能涉及应用程序回调、清理及目录更新。

分别测试以下路径：

- **预热后的稳态：**目标激活实例已经存在。
- **冷启动突发：**大量此前未激活的 Grain 标识收到首次调用。
- **持续激活周转：**激活实例被回收后不久又需要重新激活。
- **恢复：**重启或 Silo 丢失引发并发重新激活及状态读取。

记录内置的激活和停用汇总计数器及延迟，同时采集目录、存储、CPU、内存分配、垃圾回收和请求延迟等信号。若分析需要按 Grain 类型获得速率或延迟，则在 Grain 生命周期代码周围添加应用程序检测埋点。如果频繁的激活周转成为瓶颈，请从 <xref:Orleans.Grain.OnActivateAsync*> 移除不必要的工作，批量访问依赖项，并针对受影响的 Grain 类型调整[激活实例回收](../host/configuration-guide/activation-collection.md)。保留激活实例是以额外的内存占用换取更少的冷启动。

当一个存储分页构成可独立寻址的一致性边界时，可以将其建模为 Grain。立即冷激活大量分页的扫描操作，需要为每个分页承担激活、消息传递和后端访问开销。应将这种设计与更粗粒度的 Grain、通过存储后端范围查询或批量 API 实现的有界批处理、或专用索引服务进行比较。无论采用哪种设计，都应限制扇出规模。

<a id="size-silos"></a>

## 确定 Silo 规格

选择可重复部署的 CPU 和内存规格，然后测量：

- CPU 饱和程度及调度器延迟。
- 内存分配速率、垃圾回收暂停时间和工作集。
- 激活实例数量及每个激活实例的内存占用。
- 请求队列、拒绝或负载削减速率，以及尾部延迟。
- 网络连接数和吞吐量。
- 提供程序延迟和限流情况。

预留容量余量，以应对主机或故障域丢失后的激活实例重新分布和流量。选择 Silo 规格时，在重启和重新激活的影响范围与每个进程的运行时、连接及成员资格开销之间取得平衡。

即使节点 CPU 看起来仍有可用容量，CPU 限制也可能对进程进行限流。内存限制可能在托管内存分配报告内存不足异常之前，就在平台层面终止进程。根据实测稳态资源用量设置资源请求值，在理解平台策略并验证其行为的基础上设置资源上限。

<a id="find-the-operating-envelope"></a>

## 确定可运行的负载范围

使用生产环境中的运行时版本、主机规格、网络、提供程序、序列化设置及有代表性的状态数据。有效的容量测试可按以下步骤进行：

1. 定义延迟百分位数、实际完成的吞吐量、错误率、超时率和恢复目标。
1. 在集群规模固定时增加施加的负载，直到某一目标无法满足或某项资源达到饱和。
1. 在规模更大的集群上重复测试，将实际完成的吞吐量与提交的工作量一并考虑，确定可运行的负载范围。
1. 重复测试冷启动、热点键、突发流量、横向扩容、横向缩容、滚动升级、依赖项限流及 Silo 丢失等场景。
1. 在首个持续性瓶颈出现之前选择运行点，为所需的故障域预留容量余量。

将客户端可见的结果与各 Silo 的 CPU、调度器延迟、内存、垃圾回收、网络、激活实例分布、请求队列、被拒绝的工作、提供程序延迟或限流情况进行关联分析。看似均衡的集群平均值可能掩盖某个已经饱和的 Silo 或存储分区。使用所部署 Orleans 版本发出的[可观测性信号](../host/monitoring/signals.md)。

<a id="scale-out-and-in"></a>

## 横向扩容与缩容

应在达到饱和前执行横向扩容。根据持续 CPU 使用情况、调度器延迟、尾部延迟、激活压力、网关负载削减及应用程序队列深度的关联趋势进行扩缩容决策。

增加 Silo 会扩大后续资源优化放置决策的候选集合。现有活跃 Grain 继续在原 Silo 上运行。成员资格收敛后，新的激活实例可立即利用新增容量，而被回收或以其他方式停用的 Grain 可在重新激活时使用新增容量。激活实例再均衡器可以迁移符合条件的 Grain，以减少实例数量和内存占用的分布偏差；激活实例重新分区器则迁移符合条件的 Grain，以改善调用局部性。请参阅 [Grain 放置与迁移](../grains/grain-placement.md#scale-out-and-scale-in)。

应考虑：

- 调度主机、启动进程、加入成员资格及预热缓存所需的时间。
- 对集群及存储提供程序容量和连接的影响。
- 大量 Grain 在新增或剩余 Silo 上激活时产生的状态读取及序列化负载。
- 放置约束以及集中了大量工作的 Grain。
- 各故障域合计所需的最少 Silo 数量。

缩容应比扩容更缓慢。在可能的情况下，每次仅选择一个实例，采用[优雅关闭](upgrades.md#graceful-shutdown-and-scale-in)，并等待集群健康状况稳定。离开集群的 Silo 上的普通激活实例会在关闭期间停用。应为剩余 Silo 预留足够的容量，以处理重新激活、状态加载和重定向后的流量。

<a id="handle-overload"></a>

## 处理过载

无限制的队列会使过载转化为高延迟和内存压力。采取以下措施：

- 在应用程序入口实施准入控制。
- 限制队列容量和并发度。
- 设置包含下游调用在内的请求截止时间。
- 通过 <xref:Orleans.Configuration.LoadSheddingOptions> 实现客户端网关请求拒绝及流队列流量控制。
- 当某项工作负载可能使其他负载无法获得资源时，实施按租户或按键的限制。

将 <xref:Orleans.Configuration.LoadSheddingOptions.LoadSheddingEnabled> 设置为 `true`，启用运行时负载削减。达到其 CPU 或内存阈值以上时，Silo 会被标记为过载，启用客户端网关请求拒绝，并使资源优化放置优先选择未过载的候选 Silo。流队列流量控制使用 CPU 阈值暂停读取。应将阈值设置在平台硬性资源限制以下，在负载条件下验证拒绝和恢复行为，并通过托管平台的自动扩缩容机制调整集群容量。

重试也会消耗容量。在负载模型中纳入重试流量，并使用带随机抖动的指数退避、重试预算和端到端截止时间。

<a id="choose-a-tenant-topology"></a>

## 选择租户拓扑

根据所需的隔离程度和运维边界选择租户拓扑：

| 拓扑 | 优点 | 成本与风险 |
|---|---|---|
| 共享集群 | 汇集空闲容量，减少部署数量和运行时依赖项。 | 租户共享故障、部署、提供程序及容量域。应用程序通过准入控制、并发控制和资源策略实施租户配额及 noisy-neighbor（相邻租户资源争用）控制。 |
| 每租户独立集群 | 隔离容量、故障、部署、凭据和提供程序命名空间。 | 增加基础资源成本，以及升级、监控、恢复和全体集群变更的运维工作。 |
| 分片租户池 | 限制故障影响范围和集群群组规模，同时保留一定的容量共享能力。 | 需要管理租户放置、分片容量及租户迁移策略。 |

在共享集群中，按租户和键划分热点工作，实施每租户的准入及并发限制，并测试最不均衡的租户负载行为。当安全性、数据驻留、独立升级或故障和资源隔离要求硬性边界时，使用独立集群。由多个租户池组成的混合方案，通常优于假定一个无限扩展的集群或为每个小租户单独部署的方案。

<a id="revisit-the-model"></a>

## 重新评估模型

当 Grain 状态、放置策略、序列化器、提供程序、运行时版本、主机规格或流量形态发生变化后，重新评估容量。维护经过测试的应急容量调整流程，确保保留标识、网络配置及提供程序限制。
