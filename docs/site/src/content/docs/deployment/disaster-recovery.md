# 备份、还原与灾难恢复

Orleans 集群包含多种数据，其恢复要求各不相同。应清点每个提供程序，并为其确定恢复点目标和恢复时间目标。

<a id="membership-isnt-grain-state"></a>

## 成员资格数据不是 Grain 状态

集群提供程序存储描述 Silo 和网关的临时协调记录。它不包含正在运行的 Grain 激活实例，通常也不是应用程序状态的权威数据源。

| 数据 | 典型持久性 | 恢复注意事项 |
| --- | --- | --- |
| 集群成员资格 | 临时数据 | 新集群可以重新创建成员资格数据；过时的活动成员记录可能延迟或阻碍启动 |
| Grain 状态 | 由应用程序定义的持久化数据 | 根据业务要求备份、还原和验证 |
| 提醒器 | 持久化调度元数据 | 当已调度的工作必须在集群丢失后继续存在时，应保留这些数据 |
| 流提供程序状态 | 取决于提供程序 | 按需保护检查点、订阅和已排队的事件 |
| 外部数据库与副作用 | 由应用程序定义 | 协调其与 Grain 状态的一致性及去重 |
| 遥测与审计数据 | 运维或合规数据 | 独立于 Orleans 集群保留 |

不要将删除成员资格表当作还原 Grain 状态。不要以从备份还原成员资格记录代替启动新集群。

<a id="backup-design"></a>

## 备份设计

- 使用提供程序原生的一致性备份或复制功能。
- 对备份加密，并限制还原权限。
- 记录服务 ID、提供程序配置、架构版本、应用程序版本及备份时间戳。
- 当正确性要求跨越 Grain 状态和外部系统时，协调各存储的备份。
- 去重记录或操作记录的保留时间至少应覆盖最大重试和重放时间窗口。
- 在有此要求的情况下，测试提醒器、流和二级索引是否能与 Grain 状态一同恢复。

<a id="restore-procedure"></a>

## 还原流程

记录并演练以下步骤：

1. 停止或隔离对受影响状态的写入方，阻止其继续写入。
1. 选择还原点，并确定预计的数据丢失范围。
1. 将每个持久化提供程序还原到隔离的恢复环境中。
1. 使用新的集群 ID，避免恢复用的 Silo 意外加入仍然存活的集群。
1. 启动小规模金丝雀集群，验证提供程序访问、状态反序列化、提醒器、流及应用程序不变量。
1. 使用操作 ID 或业务记录对未完成的外部副作用进行对账。
1. 增加容量，有计划地切换流量，并监控错误和依赖项负载。
1. 保留故障环境，直到调查及回滚决策完成。

如果还原后的集群提供程序包含过时的活动成员记录，请遵循该提供程序的 Orleans 成员资格清理流程，或使用新的成员资格命名空间。切勿让恢复自动化程序删除位于网络分区另一侧且可能仍然存活的集群的记录。

<a id="regional-recovery"></a>

## 区域级恢复

对于有状态 Grain，主备（active-passive）比双活（active-active）更简单。备用区域应使用隔离的集群 ID，且不得处理相同的可变 Grain 键，除非存储及应用程序协议明确支持多写入方操作。

验证以下事项：

- 提供程序复制延迟及一致性。
- DNS 或入口流量切换所需的时间。
- 凭据、证书及配置的可用性。
- 恢复区域的容量。
- 结果未知的未完成请求的处理行为。
- 主区域恢复后的回切流程。

开展灾难恢复演练。未经过实际还原和验证的备份，不能证明具备恢复能力。
