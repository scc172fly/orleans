# 选择部署目标

Orleans 运行在能够为每个 Silo 提供唯一、可直接访问的 TCP 终结点，并与 .NET 主机协调进程生命周期的平台上。应选择其支持的网络模型、扩缩容控制方式、故障域放置策略及运维职责与应用程序相匹配的平台。

使用[平台要求](platform-guides.md) 作为针对应用程序可用性目标的验收门槛。然后根据以下矩阵选择仍在维护的部署指南。

<a id="target-matrix"></a>

## 部署目标矩阵

| 目标 | 支持的 Orleans 拓扑 | 终结点标识和客户端可达性 | 扩缩容与故障域 | 运维职责 | 常见提供程序选择 |
| --- | --- | --- | --- | --- | --- |
| [Azure Kubernetes Service (AKS)](azure-kubernetes-service.md) | `Deployment` 中每个 Pod 运行一个 Silo；使用独立的集群内客户端或共同托管的应用程序终结点 | Silo 通告 Pod IP。集群内客户端直接访问 Pod 的网关终结点。如果外部 Orleans 客户端需要直接访问 Pod，Azure CNI Pod Subnet 可将直接 Pod 路由扩展到已连接的网络。 | Pod 水平扩缩容、节点池自动扩缩容、可用区、拓扑分布、中断预算及受控滚动替换 | Azure 负责控制平面的运维；应用程序团队负责工作负载清单、容量、提供程序、升级和恢复 | 使用 Azure Table Storage 或 ADO.NET 实现集群成员资格；由应用程序选择持久化存储、提醒器和流提供程序 |
| [Kubernetes](kubernetes.md) | 每个 Pod 运行一个 Silo，并显式配置 Pod 名称和 IP | Silo 通告 Pod IP。客户端运行在能够路由到所有已通告网关 Pod IP 的网络上。 | Deployment 副本、特定于集群的节点扩缩容、拓扑分布、中断预算及滚动更新 | Kubernetes 运维方和应用程序团队共同负责 | 在集群附近已投入运维的高可用提供程序 |
| [Azure Container Apps](deploy-to-azure-container-apps.md) | 每个 Container App 运行一个 Silo 副本，多个 Silo 应用位于同一内部环境中 | 每个 Silo 应用在环境的私有静态 IP 上获得一对唯一的 TCP Silo 端口和网关端口 | 通过添加或移除单副本 Silo 应用进行扩缩容。通过替换应用实现受控发布。这种拓扑提供应用资源及进程冗余，但没有文档明确保证跨可用区放置。若可用性目标包含可用区放置要求，请使用 AKS。 | Azure 负责主机和环境的运维；应用程序团队负责规模有界的应用拓扑、端口分配和替换流程 | 使用 Azure Table Storage 实现集群成员资格和可选的 Grain 状态存储；在应用程序支持的情况下使用其他 Azure 数据服务 |
| [Azure App Service](azure-app-service.md) | 每个 App Service 工作实例中共同托管一个 Silo | 每个工作实例通告 `WEBSITE_PRIVATE_IP` 及为其分配的私有端口。启用私有网关映射时，受信任的应用程序客户端使用经过验证的映射。 | App Service 将多个工作实例分布在不同故障域。受支持的 Premium 计划可以启用可用区冗余。部署槽支持兼容版本的发布。 | Azure 负责工作实例及前端的运维；应用程序团队负责验证私有终结点行为、部署槽兼容性、可用区配置和容量 | 维护中的示例使用 Azure Table Storage 实现集群成员资格和 Grain 状态存储 |
| [Service Fabric](service-fabric.md) | 每个未分区的无状态 Reliable Service 实例运行一个 Silo | 每个实例通告其节点地址以及由运行时分配的 Silo 端口和网关端口 | 无状态实例数量、故障域、更新域、受监控的滚动升级及应用程序健康策略 | Service Fabric 管理放置和生命周期；应用程序负责 Reliable Service 集成及 Orleans 提供程序 | 可编译示例中使用 Azure Table Storage；适当时也可使用其他受支持的外部提供程序 |

<a id="compare-lifecycle-and-release-mechanisms"></a>

## 比较生命周期与发布机制

| 目标 | 健康检查和终止机制 | 升级和回滚机制 |
| --- | --- | --- |
| AKS | 由应用程序负责启动、就绪及存活探针；Kubernetes Pod 终止宽限期；由 PDB 约束的主动驱逐 | Deployment 滚动更新，并配合节点池的额外容量和排空控制；不兼容的变更使用隔离的 AKS 集群和 Orleans 集群 ID |
| Kubernetes | 由应用程序负责探针，结合编排器的终止宽限期及中断策略 | Deployment 或控制器的滚动发布，限制不可用实例数和额外实例容量；不兼容的变更使用独立的集群标识 |
| Azure Container Apps | 显式的启动、就绪及存活探针，以及容器终止宽限期 | 使用新的端口对创建替换用的单副本 Silo 应用；不兼容的变更使用隔离的应用集合和集群 ID |
| Azure App Service | App Service Health check、启动和部署槽预热、应用程序就绪状态以及有时间上限的主机关闭 | 兼容的变更使用预发布部署槽预热和交换；不兼容的变更使用独立的应用和集群 ID |
| Service Fabric | 通信侦听器生命周期，加上由应用程序生成的 Service Fabric 健康报告和关闭超时 | 按更新域执行受监控的滚动升级；不兼容的变更使用另行命名的应用程序和集群 ID |

## 评估其他平台是否符合要求

上述仍在维护的部署目标指南提供了完整的平台专用运维指导。使用以下辅助指南评估其他托管系统是否符合要求：

| 平台形态 | 网络指导 | 验证路径 |
| --- | --- | --- |
| 容器编排器或容器服务 | [跨多个主机运行容器](containers.md) | 证明能够按容器直接寻址或进行唯一的主机端口映射，然后对所选编排器逐一满足所有[平台要求](platform-guides.md)。 |
| 虚拟机或裸机主机 | 稳定的私有主机地址以及唯一的 Silo 端口和网关端口 | 结合基础设施团队的进程监督、故障域放置、补丁更新、扩缩容及替换自动化方案，逐一满足[平台要求](platform-guides.md)。 |

<a id="choose-the-networking-model-first"></a>

## 首先选择网络模型

Orleans 成员资格机制使用特定的 Silo 终结点标识成员。因此，所选平台需要支持以下模型之一：

- **工作负载直接寻址**：为每个 Pod、任务、容器或进程提供一个所有 Silo 均可路由到的私有地址。采用可路由 Pod 网络的 Kubernetes 和使用 `awsvpc` 任务网络的 Amazon ECS 采用此模型。
- **显式终结点映射**：为每个 Silo 提供私有主机地址或平台地址，以及唯一的已发布 Silo 端口和网关端口。Azure Container Apps、Azure App Service 和使用主机端口的容器部署采用此模型。
- **稳定主机寻址**：为每台虚拟机或物理主机提供私有地址。该主机上的每个 Silo 通告一对唯一的端口。

HTTP 入口、反向代理和共享服务虚拟 IP 用于路由应用程序流量。Orleans 传输连接仍使用成员资格中存储的各个独立终结点。有关运行时边界，请参阅[拓扑、网络与集群](networking.md)。

<a id="match-client-placement-to-the-target"></a>

## 使客户端放置方式与部署目标匹配

Orleans 客户端通过集群提供程序发现网关终结点，并直接连接这些终结点。

- 集群内客户端适合使用 Pod 覆盖网络，因为它们可以路由到每个网关 Pod IP。
- 位于已连接虚拟网络中的客户端，需要部署目标将其通告的网关地址路由到这些网络。
- 公网调用方应使用经过身份验证的应用程序 API。将 Silo 端口和网关端口限制在受信任的私有网络中。
- 共同托管的客户端使用本地 Silo，而应用程序的 HTTP 或 gRPC 入口仍走独立的平台路径。

记录客户端所在的网络，并在上线前从每个网络测试所有已通告的网关。

<a id="match-scaling-to-orleans-capacity"></a>

## 使扩缩容与 Orleans 容量匹配

平台改变进程或节点的数量。Orleans 成员资格机制接纳新的 Silo，放置机制使用可用的 Silo，并在 Silo 离开后恢复激活实例。

根据实测的应用程序信号设置扩缩容策略：

- 保持经过测试的最小 Silo 数量，并保留足以承受一个故障域失效的容量。
- 提前扩容，为新 Silo 启动、加入集群成员资格和承接激活实例留出足够的时间。
- 取消就绪状态并开始优雅关闭主机后，每次仅缩减数量有明确上限的一组 Silo。
- 协调 Pod 或进程的自动扩缩容与节点、服务计划或主机的容量。
- 对扩容、缩容、重启、提供程序降级及滚动替换进行负载测试。

请参阅[容量规划与扩缩容](capacity-planning.md) 和[优雅关闭与升级](upgrades.md)。

<a id="production-coverage-for-every-target"></a>

## 每个部署目标的生产环境覆盖要求

按照所选部署目标的指南完成以下要求，并在部署运维手册中记录特定于环境的值。

| 关注事项 | 必须达到的结果 |
| --- | --- |
| 拓扑与网络 | 每个 Silo 都具有唯一的已通告终结点，每个 Silo 都能访问所有 Silo 终结点，每个客户端都能访问所有已通告的网关终结点。 |
| 依赖项与数据 | 针对生产环境的集群成员资格、Grain 存储、提醒器、流及外部依赖项，明确制定可用性、持久性、配额、备份及恢复方案。 |
| 标识与机密 | 运行时标识和部署标识分别采用最小权限。凭据和证书的交付、轮换及到期监控均受到管理。 |
| 健康检查与生命周期 | 启动、就绪、存活、依赖项健康状态、优雅关闭及平台终止期限具有不同且经过测量的行为。 |
| 扩缩容与韧性 | 对最小容量、自动扩缩容边界、故障域分布、中断策略以及单个故障域失效后的恢复进行负载测试。 |
| 升级与回滚 | 兼容版本采用有明确范围限制的滚动替换。不兼容版本采用隔离的集群 ID 以及显式的状态和流量迁移方案。 |
| 可观测性与事故处理 | 集中式日志、指标、跟踪、部署标识、成员资格证据、告警、仪表板及事故处理命令支持在负载下进行诊断。 |
| 基础设施交付 | 基础设施和工作负载配置纳入版本管理、经过审查、能够复现，并在承接生产流量前完成验证。 |

使用[生产就绪检查清单](production-readiness.md) 进行完整审查，并通过[部署故障排查](troubleshooting-deployments.md) 了解事故诊断所需的证据。
