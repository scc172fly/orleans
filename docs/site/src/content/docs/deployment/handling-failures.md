# 故障处理

每次 Grain 调用都可能因调用方、目标 Silo、网络、运行时或依赖项故障而失败。超时或连接失败只表示调用方没有收到成功响应，并不能证明 Grain 方法没有执行。

<a id="treat-failed-calls-as-unknown-outcomes"></a>

## 将调用失败视为结果未知

考虑以下过程：

1. Grain 提交状态或调用外部服务。
1. 目标 Silo 或网络发生故障，导致响应丢失。
1. 调用方遇到超时并重试。

原始操作可能已经完成。将重试视为一个新操作可能导致重复扣款、预订、消息发送或状态转换。Orleans 可以重新激活 Grain 并重新路由后续调用，但无法推断先前调用的业务结果。

对操作分类：

- **只读**：在可以接受过时读取结果时，通常可以安全重试。
- **天然幂等**：重复设置相同的目标状态，效果不变。
- **通过去重实现幂等**：操作携带稳定的 ID，并保存结果以供重放。
- **非幂等**：重复操作会产生新的效果；没有业务对账协议时，不得自动重试。

<a id="design-idempotent-operations"></a>

## 设计幂等操作

优先采用描述目标状态的命令，或包含由原始调用方生成的操作 ID 的命令。Grain 可以：

1. 检查该操作 ID 是否已处理。
1. 如果已处理，则返回已保存的结果。
1. 在 Grain 状态中原子地执行状态转换并记录操作 ID 和结果。
1. 先持久化，再确认操作成功。

只有在已知最大重试和重放时间窗口的情况下，才能按时间或数量限制去重历史记录。如果外部系统支持幂等键，则每次重试都应传递同一个操作 ID。

Grain 状态中的去重机制并不能使独立的外部副作用与该状态成为原子操作。当单个业务操作跨越多个存储时，应使用发件箱、收件箱、流程管理器、事务提供程序或对账工作流。

<a id="bound-retries"></a>

## 限制重试

仅在满足以下条件时重试：

- 故障可能是暂时性的。
- 操作可以安全重复执行。
- 调用方的端到端截止时间尚未到达。
- 重试预算和并发限制允许再次尝试。

采用较小的尝试次数上限、指数退避和随机抖动。遵守取消请求和截止时间。避免在每一层都执行重试；多层重试的乘积可能使集群及其依赖项过载。

不要重试验证错误、授权失败、不兼容的有效载荷或确定性的应用程序异常。对于持续的依赖项故障，应使用熔断器停止重试，并明确返回降级或不可用的结果。

<a id="coordinate-multi-step-work"></a>

## 协调多步骤工作

跨 Grain 和外部服务的调用不会自动构成一个事务。协调器崩溃可能导致部分步骤已完成，而其余步骤尚未完成。

选择明确的一致性模型：

- 在选用的存储提供程序和工作负载支持时，使用 Orleans 事务。
- 采用具有持久化进度及补偿操作的流程管理器或 Saga。
- 使用发件箱/收件箱协议可靠地发布和消费消息。
- 定期依据权威业务记录进行对账。

补偿是一项业务操作，而不是内存回滚。补偿也可能失败，因此必须具备幂等性。

<a id="preserve-evidence"></a>

## 保留证据

在日志和跟踪中记录稳定的操作 ID、尝试次数、截止时间、Grain 类型和结果类别。不要将 Grain 键、租户标识符或有效载荷内容用作取值范围不受限制的指标维度。

当结果仍然未知时，应明确暴露这种状态，而不是报告成功或确定失败。为运维人员或用户提供状态查询及对账途径。

<a id="test-failure-behavior"></a>

## 测试故障处理行为

测试状态持久化之前和之后发生的故障、响应丢失、重复投递、Silo 终止、提供程序超时，以及重试窗口结束后的恢复。应验证业务不变量，而不能仅检查重试最终是否返回。
