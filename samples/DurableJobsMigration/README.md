# Durable Jobs 提供程序迁移

一个小型控制台示例将新 Durable Jobs 从具名 Azure Blob 提供程序 A 切换到
B，同时让现有 A 日志在原处排空。Aspire 使用数据卷运行 Azurite，
并在**两个依次执行的进程中调用同一个控制台项目**。
清单及验证结果显示在本地控制台输出中。

<a id="package-availability"></a>

## 包可用性

本示例使用具名日志提供程序及存储检查器 API，需要
从包含该功能的源码构建的包。在这些 API
发布前，使用仓库的本地示例包源构建本示例。
示例构建将固定的包系列版本替换为本地
打包且包含这些 API 的版本。

从仓库根目录准备该包源，并构建示例项目：

```powershell
pwsh .\samples\Build-Samples.ps1
```

这将打包当前 Orleans 源码，并使用这些
包构建示例项目。发布后，可复制出示例文件夹，并将其
`Directory.Packages.props` 中的 Orleans 包版本一起更新到
包含这些 API 的发行版本。

<a id="run-from-this-checkout"></a>

## 从当前签出目录运行

先决条件包括 .NET SDK、Aspire CLI，以及用于 Azurite 的 Docker 兼容容器
运行时。Aspire 提供本地模拟器连接。

完成上述本地包构建后，使用已解析的本地包运行现有二进制文件。
从仓库根目录执行：

```powershell
dotnet run --no-build --no-restore --configuration Release --project samples\DurableJobsMigration\DurableJobsMigration.AppHost
```

包含这些 API 的包发布并更新固定版本后，
复制出的项目可通过在 `DurableJobsMigration.AppHost` 中执行 `aspire run` 来运行。

在 Aspire 仪表板中，依次观察 `prepare` 和 `drain` 的控制台输出。
`prepare` 必须成功退出，Aspire 才会启动 `drain`。成功运行时
打印 `VERIFIED`，且两个资源的退出代码均为零。AppHost 保持运行，以便检查其仪表板
和存储；验证完成后停止它。

每次调用 AppHost 都选择新的运行 ID，以及独立的 A、B 和控制
容器。Azurite 基于磁盘的数据卷在
进程和 AppHost 重启期间保留 Blob 内容。prepare 进程在 drain
进程启动前退出。

<a id="what-is-verified"></a>

## 验证内容

1. `prepare` 选择 A 用于写入，B 用于排空，对应第一个
   部署阶段，此时每个 Silo 均能定位两个提供程序。
2. 调度一个在 30 秒后到期的 A 作业，以及另一个再过 30 秒
   到期的 A 作业。两者都超出 prepare 主机五秒的发现前瞻范围。完整
   清单必须包含两者；B 必须为空。
3. 使用 Orleans 序列化，将两个不变的 `DurableJob` 句柄保存到独立的控制 Blob 中，
   在主机正常关闭时释放分片并
   退出。下一个进程从日志恢复作业，并从
   控制 Blob 恢复句柄。
4. `drain` 启动新主机，以 B 用于写入、A 用于排空。它读取
   保存的句柄，确认 A 存储仍存在，创建新的 B 作业，并验证
   B 现已具有分片。
5. A 中的工作在新进程中恢复。首次执行故意失败；
   五秒后重试，超出原来的五秒分片
   窗口，但使用**同一个分片 ID**。B 独立执行自己的新工作。
6. 发现过程加载并拥有分片后，取消已保存的未来 A 作业句柄。
   此阶段有意将发现及激活范围扩大到两分钟，
   以便未来分片在取消前已被加载并取得所有权。
7. Blob 收据证明执行发生在 drain 进程中，保留了
   原分片 ID，并重试了 A。示例还验证已取消的
   未来作业没有收据。其执行器在
   分片开始窗口观察到空队列并删除日志。主机等待**两个**
   命名空间的分片总数均归零，然后停止。这些有界的未来
   时间使完整存储排空演示可在三分钟内完成。

收据是以作业 ID 为键的幂等写入。它们演示如何处理
至少一次执行：重复尝试覆盖同一个外部收据。
收据及作业日志变更独立提交。已持久化的 Blob
收据及完整清单确立示例结果。

每个进程具有三分钟超时；缺失收据、
意外路由、取消停滞或清单检查失败都会导致进程失败。
检查错误打印 `UNKNOWN` 并使运行失败。如果机器非常慢，
导致 A 工作在 prepare 进程关闭前执行，可使用新的 AppHost 运行，并设置
`Migration__DueDelaySeconds=90`（接受范围为 10–90 秒）。

<a id="applying-the-pattern-to-a-deployment"></a>

## 将该模式应用于部署

具名存储选项、目录及状态管理器工厂共享一个绑定。
用于 Grain Journaling 的默认提供程序保持独立。每个
物理命名空间应只归属于一个选定名称，并保留各分片原始的
权威存储位置直至最终删除。

新分片使用写入提供程序。现有作业保留原始提供程序，用于
执行、重试、重新调度、所有权管理、取消、压实及
删除。分片 ID 保持时间戳和 GUID 形式，序列化句柄
保持现有与提供程序无关的结构。稳态下，对于已知但未缓存的 ID，向选定的单个
提供程序直接读取元数据。迁移查询
先检查写入提供程序，再按需检查排空提供程序；失败与不存在
保持明确区分。

对于多 Silo 迁移：

- 在启用 B 创建前，将两个提供程序部署到**所有调度 Silo**，最初 A 用于写入，
  B 用于排空。
- 重启并切换为 B 写入、A 排空。若需严格的切换边界，暂停
  应用程序调度，直到所有调度 Silo 完成更新，并且之前的
  调度调用全部结束。否则滚动变更可能继续创建 A 分片，
  直至最后一个旧写入者完成。
- 保留 A 的列表查询、读取、条件更新、写入及删除权限。
  排空属于读写工作负载。
- 所有写入者切换后，要求成功完成 A 的完整清单检查。
  处理未来到期、已被拥有、处于有毒状态和无法识别的工作，以及清理
  故障。对于实时变化的存储列表，按需重复清单检查。
- 只有此时才仅使用 B 重启，并在其他使用方完成后退役 A。
  若需回滚，保持两者均被选中，切换到 A 写入并排空 B。

<a id="reading-inventory"></a>

## 读取清单

`IDurableJobsStorageInspector.InspectAsync` 使用只读目录及元数据操作读取选定提供程序的完整
`jobs/shards/` 命名空间。其
本地快照报告：

- `ProviderName` 和调用方的 `IsWriteProvider` 设置。
- `ShardCount`（包括无法识别的条目）、`OwnedShardCount`、
  `PoisonedShardCount` 及 `UnrecognizedShardCount`，均为 64 位计数。
- 可为 null 的 `OldestShardStartTime` 和 `NewestShardStartTime`。

计数描述分片，每个分片可包含许多作业；已被拥有和处于有毒状态的
类别可能重叠。时间描述已识别的分片窗口；重试及
重新调度可以将未来尝试安排到这些窗口之外。退役要求
**成功完成全量清单检查并确认总数为零，且完成全集群写入者切换**。
通过部署证据独立确认切换完成。失败或
不完整的快照视为未知状态。

<a id="cleanup-and-safety"></a>

## 清理与安全

示例保留具名运行资源及模拟器数据卷供检查。
它打印本次运行专用的控制容器；A 和 B 使用
`migration-a-<run-id>` 及 `migration-b-<run-id>`。两个阶段完成后，
在检查及收据保留期结束时，仅使用存储工具移除这三个
本次运行专用的容器，或在停止 AppHost 后移除示例的
专用模拟器数据卷。保留与其他
工作负载共享的数据卷。

对于实际 Azure 部署，将模拟器资源替换为经显式
批准的账户和工作负载标识，为存储操作做好预算，并
保护运维清单输出。将应用程序的身份验证及授权控制
应用于运维和变更接口。
